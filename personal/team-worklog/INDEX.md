### 🔴 2-1. 조회 분할 규칙 (2026-08-05 개정 · 강제)

**평일은 하루씩, 주말만 묶는다. 주당 6회.**

|---|---|---|---:|
| 1~5 | 월 · 화 · 수 · 목 · 금 | 각 1일 | 1 |

**실측 근거** (17명 기준)

| 묶음 | 호출/주 | 최대 응답 | 판정 |
|---|---:|---:|---|
| **평일 1일 + 토일 묶음** | **6** | **907 KB** | ✅ **채택** |
| 월화/수목/금토일 | 3 | 1,144 KB | ⚠️ 여유 5% — 폐기 |
| 주 단위 | 1 | ~1,400 KB | 🔴 |

🔴 **타임아웃 실측선 = 약 1,200 KB.** 2026-08-04 에 9명·1.2 MB 응답으로 MCP 가 **2회 연속 타임아웃**했다(실패해도 쿼터는 차감). 6분할은 여유 25% 이상을 남긴다.
> **주말을 묶는 근거**: 확정 주차 전 구간에서 토·일 실적이 **0건**이다. 두 날을 한 번에 받아도 사실상 빈 응답이며, `collectedDays` 에는 두 날짜가 모두 기록된다.
> ⚠️ **매 수집 시 응답 크기를 기록한다. 어느 구간이든 1,000 KB 를 넘으면 그 구간을 더 쪼갠다.**
> 💡 **MCP 보다 REST 를 우선한다.** `POST /rest/api/3/search/jql` 이 같은 쿼터를 쓰면서 대용량에 안정적이다.

#### 🛑 1회 실행 = 1주차 (2026-08-05 추가 · 강제)

> **명시적 지시가 없으면 무조건 한 주차만 수집하고 멈춘다.**

| 발화 | 처리 |
|---|---|
| "워크로그 가져와" · "한주치 더 가져와" · **"이어서 진행해"** · "계속해" | **1주차만** |
| **"N주치 가져와"** 처럼 **수량 명시** | 명시한 만큼 |
| "잔여 쿼터 다 써" 처럼 **범위 명시** | 그 범위까지 |

- **잔여 쿼터가 넉넉하다는 것은 실행 범위의 근거가 아니다.**
- 1주차를 끝내면 **결과를 보고하고 멈춘다.** 다음은 사용자가 다시 지시할 때만.
- **"이어서 진행해" = "한 주 더"** 다. "쿼터 소진까지" 로 해석하지 않는다.

> 📌 **왜 생겼나** — 2026-08-05 에 "오늘만 20회 늘리고, 이어서 진행해" 를 쿼터 소진으로 해석해 **3주를 연속 처리(19회)** 했다. 그때까지 사용자는 매번 "한주치 더" 로 **한 주씩** 진행하고 있었다. 범위를 임의로 넓힌 초과 실행이다.

#### 트리거 B — "이번주꺼 / 저번주꺼 가져와"

`W_now` 와 `W_now−1` 을 **둘 다** 수집한다. **확정하지 않는다.** (둘 다 `진행`)

#### 자동 승격
`W_now−1` 이 `W_now−2` 가 되면 위 선정 규칙의 대상이 되어 재수집 후 확정된다. **별도 로직이 필요 없다.**

**② 월간상태**

| 상태 | 조건 |
|---|---|
| ⏳ **대기** | 기본값 |
| ✅ **확정** | **사용자가 명시적으로 월간 보정·확정을 요청한 뒤** |

## 3. 🔑 호출 절감 설계

**① 오버플로 이슈**
인라인 `worklog` 필드는 **`maxResults=20` 고정**이다. `total > 20` 인 이슈는 본문이 잘리므로 `/issue/{key}/worklog?maxResults=1048` 로 따로 받아야 한다. 실측상 100개 이슈 중 **12개**가 해당한다(`WORK-16309` 129건, `WORK-16384` 110건 등 — 월간 버킷형 이슈).

**② 변경 감지**
search 응답에 이슈별 `worklog.total` 이 함께 온다. [issue-cache.json](./issue-cache.json) 의 스냅샷과 **숫자만 비교**해서 변한 이슈만 다시 받는다. → 현행화가 대부분 **search 1회로 끝난다.**

**③ 캐시는 색인만 — 본문을 들고 있지 않는다**
오버플로 이슈를 통째로 받으면 그 엔트리들은 여러 과거 주차에 걸쳐 있다. 캐시에 쌓지 말고 **즉시 각 주차 파일로 분배**하고, 캐시에는 `{ issueKey: { total, lastFetched } }` 만 남긴다. 덕분에 캐시가 수십 KB로 유지되고 매 실행 재커밋해도 부담이 없다.
> 이때 유입된 주차는 그 이슈 것만 있어 불완전하므로 **🟡 부분** 으로 표시한다. 완료로 오인하면 안 된다.

## 4. ⚠️ 데이터 정합성

**① 클라이언트 재필터 필수**
JQL `worklogAuthor` 와 `worklogDate` 는 **서로 묶이지 않는다.** "9명 중 누가 기록한 이슈" AND "그 기간에 누가 기록한 이슈"로 각각 걸릴 뿐이다. 받은 뒤 `accountId ∈ 로스터` **AND** `date ∈ 주차범위` 로 다시 걸러야 남의 워크로그가 섞이지 않는다.

**② 삭제 감지**
현행화 시 **이전 수집에 있었으나 이번에 없는 `worklogId`** 는 삭제된 것이다. 덮어쓰기만 하면 유령 데이터가 남으므로 해당 주차는 **전체 교체**하고 삭제분을 `manifest.json` 에 기록한다.

**③ 0건 주차도 확정 처리** — 재조회를 막는다.

**④ `ensure_ascii=False` 고정** — 한글 이스케이프 시 23% 팽창하고 diff가 무의미해진다.

## 5. 파일 구조

```
personal/team-worklog/
├─ INDEX.md            이 문서 — 현황판·규칙
├─ roster.json         팀원 9명 (기계 판독)
├─ SUMMARY.md          누적 롤업
├─ manifest.json       주차별 상태·수집일·엔트리수·호출수
├─ issue-cache.json    이슈별 total 스냅샷 (색인만) · 🚫 gitignore
└─ data/
   └─ YYYY-MM-DD.json  ← 파일명 = 그 주 월요일
```

> **주차별 분리 이유**: 단일 파일이면 매주 2 MB 전체가 재커밋돼 히스토리가 부푼다. 분리하면 변경분만 커밋되고, 확정된 과거 주차는 다시 건드리지 않는다.
> **ISO 주차(`2026-W32`)를 쓰지 않는 이유**: 연말연시에 `2026-W01` 이 2025년 12월을 가리키는 경계 문제가 있다. 1년치를 쌓으면 반드시 밟는다.

### 📦 로우데이터 보관 (2026-08-05 확정)

├─ 2026-07-27/   mon.json  tue.json  wed.json  thu.json  fri.json  weekend.json

> 실측(`박인욱 2026-08-03`): 오전 5개 묶음은 50%, 오후 단독 3개는 **100%** 로 복원됐다.

### 🔴 표시 규칙 — 수집은 전부, 표시는 확정·진행만 (2026-08-06 확정 · 강제)

> **수집·저장은 전부 한다. 현황판·캘린더에는 `확정`·`진행` 주차만 올린다.**

| 계층 | 범위 |
|---|---|
| **수집·저장** (`data/*.json` · `raw/`) | 🟢 **전부** — 부분 주차·과거·미래 포함. 손대지 않는다 |
| **현황판** (`wl.py status`) | ✅ **확정 + 🔵 진행만** |
| **캘린더** (`wl.py viewer` → `data.js`) | ✅ **확정 + 🔵 진행 주차만** |

**제외분은 지우지 않고 한 줄로만 요약한다.**

```
⚪ 미표시(부분) 34주 · 319건 · 1084.5h — 데이터는 보관 중. 수집·확정되면 표에 올라온다
```

> **왜** — 오버플로 버킷 이슈(`[26년 상반기] 서비스개발팀 근태 관리` 등)는 한 번 받으면 **1~2건씩 과거·미래로 흩뿌려져** 주차를 수십 개 만든다. 실측: 실제 수집은 5주인데 표에는 **39주**가 떴고, 그중 34주가 1~10건짜리 부스러기였다(2025-06 · 2026-09 까지).
> 그 데이터 자체는 유효하므로 **버리지 않는다.** 다만 진척·집계를 오독하게 만들므로 **표시에서만 제외**한다. 해당 주차를 실제로 수집해 `확정`/`진행`이 되면 자동으로 올라온다.

⚠️ **집계(주간 상태·월간·전체·팀별)도 표시 대상 기준으로 낸다.**
- 실측 차이: 전체 39주 1,120건 3,120h → **표시 5주 801건 2,036h**

📌 참고 — `collectedDays`(수집일 n/7)는 `wl.py day` 만 채우고 `wl.py overflow` 는 건드리지 않는다. 표시 기준은 아니지만 **"실제로 받은 주차인지"** 를 나타내므로 현황판 `수집` 열로 노출한다. 예: `2026-07-27`은 `진행`이라 표시되지만 `0/7` 이라 수치가 실제보다 적다.

#### ❌ 생성일 기준 JQL 은 불가능

JQL 이 지원하는 워크로그 조건은 **`worklogAuthor` · `worklogDate`(=`started`) · `worklogComment`** 3개뿐이다. `worklogCreated` 같은 필드는 없고, `created` 는 **이슈** 생성일이라 무관하다.

#### ✅ 대신 이슈 `updated` 가 신호가 된다 (검증 완료)

**워크로그를 추가하면 그 이슈의 `updated` 가 갱신된다.** 실측으로 확인했다:

```
WORK-16309   이슈 updated          2026-08-05T18:57:04
             마지막 워크로그 created  2026-08-05T18:57:04   ← 초 단위까지 일치
```

(같은 이슈의 `total` 이 138 → 140 으로 늘어난 것을 캐시가 감지한 시점과도 일치)

#### 현재 `issue-cache.json` 의 맹점

```json
"WORK-16309": { "total": 140, "lastFetched": "2026-08-05" }
```

**건수(`total`)만 비교**하므로 아래를 놓친다.

| 변경 | `total` | 감지 |
|---|---|---|
| 워크로그 추가 | 140 → 141 | ✅ |
| **시간 수정**(3h→5h) | 140 → 140 | 🔴 |
| **코멘트 수정** | 140 → 140 | 🔴 |
| **1건 삭제 + 1건 추가** | 140 → 140 | 🔴 |

#### 제안 구조 — 발견 / 현행화 2축

| 역할 | 방식 | 주기 |
|---|---|---|
| **발견** | `worklogDate` 주차 조회 (현행 유지) | 새 주차 수집 시 |
| **현행화** | `key in (…) AND updated` 비교 → 변경분만 재조회 | 주 1회 스윕 |

**비용 시뮬레이션** (2026-08-06 기준 보유 이슈 **233개**)

| 단계 | 호출 |
|---|---:|
| 233개 `updated` 일괄 조회 (`key in` 은 1회 100건) | **3** |
| 변경 감지분만 워크로그 재조회 | +α (1~3) |
| **주 1회 총비용** | **약 4~6회** |

캐시에 `updated` 필드를 추가하면 된다(`total` 은 재조회 후 검산용으로 유지).

#### ⚠️ 한계

- `updated` 는 **워크로그 전용이 아니다.** 코멘트·상태·필드 변경에도 올라가 **헛걸음**이 생긴다.
- 버킷 이슈(`[26-3Q] 모바일개발팀 일반 업무` 등)는 워크로그 외 변경이 드물어 헛걸음이 적다. **20건 이상 이슈 10개로 대상을 좁히면** 비용·헛걸음이 더 준다.
- 어느 워크로그가 새 것인지는 알려주지 않아 **이슈 단위 전량 재조회**가 필요하다. 단 `worklogId` 가 PK라 중복은 쌓이지 않는다.
