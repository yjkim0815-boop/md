# 🛠️ WORKLOG — 출석체크 개편 (2026-07-24)

## 배경 / 목적
해피포인트 **앱**(ha_api)의 출석체크(스탬프) 리워드 정책을 개편한다.
- 기존 정책은 보상 획득까지 **한 달**을 기다려야 하고 소수(추첨 10명)만 실질 혜택 → 참여 동기·리텐션 저하.
- 개편 목표: **주 단위**로 짧게 끊고, 7일 완주 시 **전원에게 확정 소액 보상(5P)을 실시간 지급**해 즉시성·참여율을 높인다. 큰 보상(1만P)은 추첨으로 유지하되 규모 조정(10명 → 3명).

## 요구사항 (AS-IS → TO-BE)

### AS-IS (기존)
- 주기: **월 단위**. 1개월 출석 **만근** 시.
- 보상: **추첨**하여 **1만 포인트**를 **10명**에게 지급.
- 확정 보상 없음(추첨 당첨자만 수령).

### TO-BE (변경)
- 주기: **주 단위**. 한 주 **출석 7일 전부 완료** 시.
- 확정 보상: **전원 무조건 5포인트 실시간 지급** (7일째 출석 완료 즉시 적립).
- 추첨 보상: **1만 포인트**를 **3명**에게 지급 (기존 10명 → **3명**으로 축소).

### 변경 요약표
| 항목 | AS-IS | TO-BE |
|------|-------|-------|
| 집계 주기 | 월(만근) | **주(7일 완주)** |
| 확정 보상 | 없음 | **전원 5P, 실시간 지급** |
| 추첨 보상 | 1만P × **10명** | 1만P × **3명** |
| 지급 시점 | 월 마감 후(추첨) | 5P=완주 즉시 / 추첨=주기 마감 후(주기 확정 필요) |

## 확인 필요 (Open Questions) — ⚠️ 미확정
> 아래는 구두 전달 기준 기록. 구현 착수 전 기획 확정 필요.
1. **추첨(1만P×3명) 주기**: "주 단위"인지, 여전히 "월 단위"인지 미확정. ("3명**씩**" 표현 → 주기 반복 가능성). → 확정 요청.
2. **추첨 응모 자격**: 해당 주 7일 완주자 대상인지, 참여자 전체 대상인지.
3. **5P 지급 중복/반복**: 매주 완주 시 매주 5P 지급(반복) 가정. 월 상한/누적 상한 여부 미확정.
4. **주(week)의 경계 정의**: 월~일 고정 vs 사용자 시작일 기준 롤링 7일. 미완주 주는 이월 없이 리셋인지.
5. **기존 월 만근 로직 처리**: 개편 시점에 진행 중이던 월 진행분의 정산/폐지 방식.
6. **정책 시작일 / 대상 버전**: 앱 버전 게이팅, 오픈 일정.
7. **포인트 종류**: 지급 대상이 해피포인트 본 포인트인지 별도 이벤트 포인트인지(회계/소멸정책 상이).

## 영향 범위 (코드/DB) — 추정, 확정 아님
> 실제 파일 매핑은 착수 시 `services/<도메인>` + 대응 `mybatis/**` mapper를 짝으로 확인. (INDEX 참조)
- **서비스 도메인**: `services/stamp`(출석/스탬프 집계) + `services/point` 또는 `services/pointstation`(포인트 적립 지급). 컨트롤러는 `api.controller.api/` 또는 `rest/`.
- **DB(`jdbc/ha` Oracle 메인)**: 출석 집계 단위를 월→주로 바꾸는 스키마/컬럼 영향 가능(주차 키, 완주 플래그, 지급 이력). 추첨 이력 테이블의 당첨 인원(10→3).
- **MyBatis**: `mybatis/default`(및 필요 시 해당 도메인) mapper의 집계/지급 쿼리.
- **배치/스케줄**: 월 마감 배치 → 주 마감(추첨) 배치로 주기 변경. (ha_api 내 스케줄 위치 확인 필요)

## ECC 적용 포인트 (참조: [ecc-reference.md](../../shared/ecc-reference.md) §4)
> ha_api = Spring MVC + MyBatis WAR(Java8). Boot/JPA 예시는 개념만 차용.
- **포인트 "실시간 지급"은 금전성 트랜잭션** → `springboot-security` 체크리스트 + `security-review` 기준 우선 적용:
  - **중복지급 방지**: 동일 사용자·동일 주차 재요청/동시요청에 대한 **멱등성 + 유니크 제약**(주차별 지급 이력 1건) 필수. 동시성(따닥 클릭·재시도) 레이스 컨디션 검토.
  - **트랜잭션 경계**: 출석 완주 판정 → 5P 적립을 원자적으로. 부분 실패 시 적립/차감 정합성 보장.
  - **SQL 인젝션 방지**: MyBatis **`#{}`** 파라미터 바인딩 (동적 정렬 등 불가피 시 화이트리스트).
  - **인가**: 본인 계정 출석/지급만 가능(IDOR 방지), 세션/토큰 검증.
- **추첨 로직**: 난수/공정성·재현성(감사 로그), 당첨 인원 상수화(매직넘버 금지 — 3, 10000 등은 설정/상수로). `rules/common/coding-style.md`.
- **기존 패턴 우선**: 신규 REST 설계 시 ha_api의 기존 `api/`·`rest/` 관례를 따른다(무리한 재설계 금지). `rules/common/patterns.md`.
