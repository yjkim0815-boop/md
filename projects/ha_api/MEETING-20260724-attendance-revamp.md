## 1. 배경 / 문제 정의
- 개편안: **주 단위 출석 7일 완료 시 포인트 지급**. → 관련 기획 문서 참조.
- **핵심 문제**: 지급 트리거가 주 경계에 걸려 있어 **일요일 00:00에 사용자가 일시에 몰림**(트래픽 스파이크). 지급 처리·대상자 선정이 이 시점에 집중되면 부하·과발급·선착순 왜곡 위험.
- 이를 해소하기 위해 본 회의를 진행.

## 2. 논의 항목 및 결정

### 2-1. 당첨 확률 공개 여부 → **법무 검토 필요**
- 본 리워드는 **가챠(뽑기)가 아님** → 원칙적으로 **확률을 공개할 의무/이유는 없다**는 것이 기본 입장.
- 다만 **참여 과정에서 광고를 시청**하는 구조이므로, **"광고 시청을 고객이 지불한 본인 재화로 볼 수 있는가"** 에 따라 확률 공개 의무가 발생할 소지 있음.
  - → **[법무검토]** 광고 시청 기반 참여가 유료 재화 소비에 준하는지, 그렇다면 확률형 정보 공개 대상인지 검토 요청.

### 2-2. 트래픽 방어 → **NetFUNNEL(가상대기열)로 해결**
- 일요일 00:00 스파이크는 **NetFUNNEL(넷퍼넬) 페이지 단위 대기열**로 완충.
- **날짜 경계 처리 원칙**: **전날 진입한 세션은 날짜가 바뀐 뒤의 출석체크를 할 수 없게** 한다. (대기열에서 자정을 넘겨 진입 → 이전 날짜 기준 출석 인정 방지)
- **hpc(해피포인트카드 본 서비스)로 향하는 일요일 00:00 트래픽 방어** 포함. → 앱 출석 트래픽이 본 서비스로 전이되지 않도록 차단/완충.
  - → **[확인필요]** NetFUNNEL 적용 범위(앱 출석 API 한정 vs hpc 연계 경로 포함), 대기열 정책(동시 처리량·타임아웃).

### 2-3. 대상자 선정 시점·기준 → **토요일 / 순수 3회 출석**
- **대상자 선정을 토요일에** 미리 수행 (일요일 00:00 집중을 회피하기 위해 선정 시점을 앞당김).
- 선정 기준: **"순수 출석 3회"** — **광고 시청분은 제외**한 실제(순수) 출석만 카운트.
  - → **[확인필요]** "순수 3회"와 상위 기획의 "주 7일 완주"의 관계. (7일 완주 = 5P 확정지급 조건 / **순수 3회 = 추첨(1만P) 응모 자격**으로 분리되는 것으로 추정 — 확정 필요.)
  - → **[확인필요]** "광고 출석"과 "순수 출석"의 정의·구분 로직(하루 복수 출석 가능 여부 포함).

### 2-4. 지급 방식 → **사전대상자 방식 선호, 실시간 랜덤 지양**
| 방식 | 과발급 리스크 | 결론 |
|------|--------------|------|
| **사전 대상자 선정** | **없음** (선정 인원 = 지급 인원, 통제됨) | ✅ **선호** |
| **실시간 랜덤** | 있음 (동시성으로 정원 초과 지급 가능) | ⚠️ 과발급 감안 필요 → **가급적 지양** |
- 즉, **토요일에 사전 대상자를 확정**해두면 과발급이 원천 차단됨(2-3과 연결).

### 2-5. 지급 정책 원칙 → **선착순 지양**
- **가급적 "선착순"이 아니도록** 설계. (일요일 00:00 몰림 시 선착순은 서버 부하·형평성 문제를 키움 → 사전 선정/추첨 기반으로 유도.)

---

## 3. 합의 방향 (요약)
1. 트래픽: **NetFUNNEL 대기열 + 날짜경계 차단 + hpc 트래픽 방어**로 일요일 00:00 스파이크 완화.
2. 대상자: **토요일 사전 선정**, **순수 출석 3회**(광고 제외) 기준.
3. 지급: **사전 대상자 방식**(과발급 없음) 우선, **실시간 랜덤·선착순 지양**.
4. 컴플라이언스: **광고=재화 여부에 따른 확률 공개 의무 법무검토** 선행.

## 5. ECC 적용 메모 (참조: [ecc-reference.md](../../shared/ecc-reference.md) §4)
- **사전 대상자 방식 = 과발급 원천차단**은 ECC `security-review`의 "실제 악용/오류 시나리오 성립 여부 검증" 관점과 일치 — 실시간 랜덤 채택 시 **동시성 과발급**이 성립하므로 사전선정이 안전.
- 실시간 지급 경로가 남는다면: **멱등성 + 주차별 유니크 제약 + 트랜잭션 원자성**(중복/과발급 방지), MyBatis **`#{}`** 바인딩, 본인계정 인가(IDOR) — `springboot-security` 체크리스트.
- 당첨 인원·포인트 값(3, 5, 10000)은 **상수/설정**으로(매직넘버 금지) — `rules/common/coding-style.md`.
