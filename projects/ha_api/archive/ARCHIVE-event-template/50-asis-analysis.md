# 🕰️ AS-IS 분석 (개편 전 구조)

> 출처: 착수보고 업무흐름도·이벤트 현황표 + AS-IS 샘플(`eventView.jsp`·`eventProc.jsp`·테이블/데이터)

## 1. 개발 흐름

### 요약 흐름
```text
마케팅/기획 요청(Jira JSM)
→ PPT 기획안
→ Figma 디자인
→ FE: eventView.jsp 개발
→ BE: eventProc.jsp 개발
→ Stage 검증
→ 운영 반영
```

### 상세 업무흐름 (MKT 프로모션, 착수보고 도식)
```text
프로모션 기획안 전달
→ FE 퍼블리싱
→ 리소스 업로드
→ 리워드 셋팅(Rule)
→ BE 기능개발
→ 기획안 수정          ← 되돌림
→ QA
→ 프로모션 오픈
→ 수정                 ← 되돌림
→ 종료
```
> 🔴 오류수정·기획변경 시 **다수의 되돌림 루프**가 발생. 이것이 공수 예측 불가의 직접 원인.

## 2. 문제점 (착수보고 4번)
1. **이벤트별 개별 JSP 개발** — 반복 기능도 이벤트마다 재구현
2. 이벤트마다 복합기능이 달라 **명확한 공수산정 불가**
3. 주요 이벤트는 **기능·디자인 수정이 지속 발생 → 추가공수 누적**
4. 리소스 반영이 **파일 업로드 방식** (2차 개선내용에 "프로모션 추가수정 시 파일업로드 등의 업무절차 개선"으로 명시)
5. AS-IS는 **"프로모션 요구사항 분석 후 FE/BE 공동개발 착수"** — 건마다 개발자 투입이 전제
6. 화면 스크립트와 서버 처리 로직이 **분산**
7. **개발자 의존도 증가** — 운영자가 직접 구성 불가
8. 이벤트 **복사·재사용 어려움**

## 3. AS-IS 코드 구조

| 파일 | 역할 | 실측 크기(샘플) |
|------|------|-----------------|
| `eventView.jsp` | 이벤트 화면(FE) | 약 **29KB** |
| `eventProc.jsp` | 이벤트 처리(BE) | 약 **100KB** |

→ **이벤트 1건당 이 규모의 JSP 2개를 개별 작성**. 샘플 2건(`이벤트1`·`이벤트2`) 모두 동일 패턴.

## 4. AS-IS 데이터 구조

| 테이블 | 역할 |
|--------|------|
| `EVENT` | 이벤트 전체 마스터 (PK `EVENTSEQ` **NUMBER**) |
| `EVENT_OFFR_META` | 이벤트 전체 리워드 정보 |
| `EVENT_PROC_RULE` / `EVENT_PROC_BTN` | Rule 엔진 (→ [31](./31-ddl-event-proc.md)) |
| **`EV_EN_{YYMMDD}_{seq}`** | **이벤트별 리워드 이력 — 동적 테이블 생성** |

### 🔴 동적 리워드 이력 테이블
- 예: `EV_EN_260512_30537`, `EV_EN_260519_30576`
- **이벤트마다 테이블을 새로 만든다** → 스키마 오브젝트 무한 증식, 통합 조회·통계 어려움
- 샘플 데이터 크기: **약 80MB / 20MB** (2건만으로)
- 이것이 AS-IS의 가장 큰 데이터 부채이며, 모니터링 기능(1차)이 필요해진 배경

## 5. 이벤트 현황 실측 (착수보고 "5. 이벤트 현황")

> ⚠️ **AS-IS 기준 현황치**다. 문서 어디에도 "고도화 후 공수 X% 절감" 형태의 **사후 정량 성과는 없다.**

| 구분 | 월 건수 | FE 공수 | BE 공수 | 역할 |
|------|--------:|---------|---------|------|
| 단순안내 | 20~30건 | 2H 이하 | – | FE: 퍼블리싱 |
| 단순 리워드형(허들 유/무) | 10~20건 | 2~4H | – | FE: 퍼블리싱 / **기능등록(Rule)** |
| 참여형(룰렛·퀴즈·투표·난수·게임·스탬프) | 4~8건 | 2~8H | **2~5H** | FE: 퍼블리싱/기능등록 + **BE: 기능개발** |
| MKT(대형·복합) | 2~4건 | 8~24H+ | **4~20H+** | FE: 퍼블리싱 + **BE: 기능개발** |

### 도출 관계 (계산치 — 문서 명시 아님, **추정**)
- 월 이벤트 총량 **36~62건**
- **BE 공수 불필요 구간**(단순안내 + 단순 리워드형) = 월 **30~50건** → 전체의 **약 76~83%** 가 이미 Rule 등록만으로 처리(= 정형화 커버리지)
- **BE 개발 필요 구간** = 월 **6~12건**, BE 공수 총 **약 20~105H/월**
- 1차 Rule 확장(리워드 소진 시 추가 포인트 · 난수입력 참여횟수 · 리워드 선택발급 · 출첵/스탬프/댓글 참여여부)은 **"참여형" 구간**(월 4~8건, BE 2~5H)을 Rule화 대상으로 겨눈 것으로 **추정**

> 💡 **전략 해석**: 이미 76~83%가 Rule로 처리되던 상황에서, 1차는 **남은 참여형을 Rule로 흡수**하고, 2차는 **FE 퍼블리싱까지 템플릿화**해 개발자 개입을 더 줄이는 순서로 설계됐다.

## 6. 연계 시스템 (AS-IS/TO-BE 공통)

| 시스템 | 역할 |
|--------|------|
| **HPC** | 회원 · 인증 · 포인트 · 승인 |
| **CMS** | 쿠폰 발급 및 관리 |
| **POS** | 매장 할인 및 결제 |
| **이벤트 서버** | 참여 및 리워드 오케스트레이션 |

## 7. TO-BE 대비 (요약)
```text
[AS-IS] 요청 → 기획안 → 디자인 → FE JSP → BE JSP → 검증 → 반영  (개발자 필수)
[TO-BE] 운영자 → 기본정보 → 프로모션폼 선택 → Rule 등록 → Meta 입력 → 미리보기 → 발행  (개발자 선택적)
```
