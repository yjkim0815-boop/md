## 2. 4단계 로드맵 ↔ 2차 실행 결과 매핑

| 단계 | 계획 내용 | 2차(`HA26H197`) 실행 결과 |
|------|-----------|---------------------------|
| **1차** | 이벤트 마크업(BO) **Label 기능** — Label 부여 / 필터링 + **기존 이벤트 복사 기능** | ✅ `EVENT_TMPL_FORM.FORM_TYPE_NM` 유형 뱃지로 구현 (Label 결과보고 별도 KEEP) |
| **2차** | **프로모션폼(form) 기본기능** — 양식 선택 페이지, 쉬운 UI → **개발인력 투입 없이 이벤트 셋팅** | ✅ Step2 프로모션폼 선택·연결 (`EVENT_TMPL_FORM` / `EVENT_TMPL_BRIDGE`) |
| **3차** | **Rule Based 컴포넌트 단위 모듈화 (클래스 바인딩)** — 클릭 / 조회 / 입력 / 체크 등 상호작용 기능화 | ✅ `ha-btn-{slotNo}-{role}` 표준 class + 공통 JS |
| **4차** | **프로모션폼 + Rule Based 컴포넌트 연동** — 기능제한 제약 해소, **비정형 요구 대응** | ✅ Step2에서 프로모션폼↔Rule 연동 완료 |

## 3. 부가 구상
- **외부 API 등 일회성 특수기능에 대한 스크립틀릿 제공**
  → 정형 템플릿으로 커버 안 되는 비정형 요구를 스크립틀릿으로 흡수하는 안전판

## 4. 운영자 작업 흐름 (계획)
```text
프로모션폼 선택
→ 폼 마크업
→ 폼 커스터마이징
```
- 필요 시 **생성된 컨텐츠를 이벤트 마크업과 연동**해 추가 커스터마이징

## 5. 기획 의도 해석
- **"개발인력 투입 없이 이벤트 셋팅"** 이 2차의 핵심 KPI
- 1차가 **백엔드 기능(Rule)** 을 정형화했다면, 2차는 **프론트 화면(Form)** 까지 정형화해 **개발자 없이 완결되는 범위**를 확대
- 4차(연동)를 마지막에 둔 이유: 폼(화면)과 Rule(기능)을 각각 독립 완성한 뒤 결합해야 **조합 폭발을 피하고 재사용성이 확보**되기 때문 (**해석 — 문서 명시 아님**)
